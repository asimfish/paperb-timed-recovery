# NA2：按墙钟节奏的原生闭环，三档声明延迟（2026-10-20）

**问题：** 让物理仿真与墙钟锁步，worker 推理时物理照常推进。推理延迟会吃掉多少个物理 tick？动作块里的 8 个计划槽位，有多少在返回时已经作废（STALE）？

**结论：** 三档延迟各一个正式原生案例，各只启动一次，退出码都是 0。离线 reader 的 17 项检查三案全部通过。经过的 tick 数和作废比例都落在执行前声明的预测范围内。

## 设置

- **沿用 NA1 的部分：** 场景、PhysX 参数、dt = 1/240 s、相机、预热 240 tick、P0 工程 checkpoint 与 CPU worker。日志组件换成 v0.4（语义与 v0.3 相同，每条事件开销恒定）。
- **节奏：** 每个物理 tick 固定占 16.667 ms 墙钟，即 4 × dt，实时比 0.25。这台机器上物理步进中位约 4 ms，日志每条事件 fsync 约 2 ms，做不到 1:1 实时。
- **渲染不计入物理时间：** 只在发推理请求之前、且没有推理在途时渲染。渲染耗时（中位约 46–50 ms）从节奏锚点中扣除，只记录不计入；推理在途期间物理始终按节奏推进。
- **请求与延迟：** 每 24 tick 发一次请求，任务共 2,400 tick（仿真 10 s）。worker 算完后，按声明延迟（0、50、150 ms）等待再返回。

## 结果

| 声明延迟 | ticket 数 | 请求到返回经过的 tick | 8 槽中作废 | 按时生效 | 超限拒绝 |
|---|---|---|---|---|---|
| 0 ms | 14（第 317 tick 守卫停止） | 1：7 次，2：7 次 | 21/112（19%） | 25 | 62，另有 4 条在停止时丢弃 |
| 50 ms | 100 | 3：1，4：17，5：82 | 481/800（60%） | 102 | 217 |
| 150 ms | 100 | 10：9，11：91 | 800/800（100%） | 0 | 0 |

- **worker 实测：** 计算时间中位 5.5–5.6 ms；声明的等待实际为 50.07 ms 和 150.07 ms。经过的 tick 数约等于 ⌈(计算 + 延迟 + 进程间通信) / 16.667 ms⌉，再加至多 1 个 tick 的轮询粒度。
- **恒等式：** 每个 ticket 的作废槽数都恰好等于 min(8, 经过的 tick 数)，reader 逐个核对。这是机制本身的恒等式，不是新的发现；新的是上表里延迟与经过 tick 数之间的实测关系。
- **节奏保真度：**
  - 非渲染 tick 的间隔中位正好 16.67 ms；
  - 95.6% / 96.3% / 99.6% 的 tick 延迟在一个周期以内；
  - 推理在途期间，每个经过的 tick 实际占用的墙钟中位为 12.0 / 14.8 / 15.8 ms；
  - 在途期间出现超过一个周期滞后的 ticket 分别有 0 / 1 / 0 个。
- **视频：** 三案并排，每个请求 tick 一帧，共 100 帧，10 fps 播放即仿真实速。0 ms 案例停止后，它那一栏显示“守卫停止”的说明面板，不重复它的最后一帧。150 ms 案例里机械臂始终不动，因为每个动作块在返回时都已全部作废。

## 必须同时说明的限制

- **按真实时间算，影响还要大 4 倍。** 节奏因子是 4，所以 16.67 ms 墙钟对应 4.17 ms 物理时间。如果按 1:1 实时运行，150 ms 延迟会吃掉约 36 个 tick，50 ms 约 12 个。也就是说，在 1/240 s 的控制频率下，8 槽动作块只覆盖约 33 ms 物理时间，即使中等延迟也会让整块作废。这支持在方法中显式建模延迟，但本轮没有测试任何这样的方法。
- **0 ms 案例在第 317 tick（仿真 1.32 s）触发了状态守卫。**
  - 原因：第 316 tick 生效的 P0 目标跳变很大（关节 3 一步 1.96 rad，两个手指目标不对称：0.0148 / 0.0105）。下一个观测状态违反了守卫，案例按协议停止。
  - 记录缺口：触发守卫的那个状态，只在日志中保存了摘要，逐 tick 记录在守卫判断之前就退出了。所以具体是哪个关节、什么数值越界，无法确定。下一版要在守卫触发时把该状态的 q/qd 写入记录。
  - 按预算不重跑。该案例只有 14 个 ticket，但这 14 个的经过 tick 数（1–2）与 CPU 预演（1–2）一致。
- **不是策略结果。** P0 仍是不准确的工程模型：在已提交的目标中，0 ms 案例有 62/91、50 ms 案例有 217/319（均约 68%）超出关节限位被拒绝。
- **不涉及以下内容：** 任务完成、受力资格、化学终点、S/F/R 准入、M/B3 对比、真机，以及 E02 要求的强计时器基线。
- **服务器负载：** 运行期间 load average 约 60–92，GPU 与其他用户共享。本流程只读取 GPU 显存，不向其他进程发送任何信号。

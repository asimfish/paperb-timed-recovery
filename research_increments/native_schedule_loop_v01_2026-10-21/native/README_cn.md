# NA3：延迟补偿调度 vs 朴素调度（2026-10-21）

**问题：** 在与 NA2 相同的墙钟节奏下（每 tick 16.667 ms），只利用自己观测到的公开信息去补偿推理延迟，能否让计划的动作在返回时仍可执行？还剩下哪些失败？

**结论：** 补偿调度把作废槽位从 60.5%（50 ms）和 100%（150 ms）降到约 1%。剩下的作废几乎都来自第一个 ticket：那时还没有任何延迟观测，所以第一个动作块按朴素方式计划。

四个正式原生案例按固定顺序运行，各启动一次，退出码都是 0，离线 reader 18/18 通过，没有触发状态守卫。

## 方法

- **朴素调度：** 在 tick k 发出请求，动作块计划在 k+1…k+8。
- **补偿调度：** 取最近 8 次返回实际经过的 tick 数的最大值作为 L̂（还没有返回时为 0），把动作块计划在 k+L̂+1…k+L̂+8，并把对应的时间偏移 (L̂+1…L̂+8)·dt 作为模型输入。只用本 owner 已观测到的返回时刻，不读取声明延迟或任何私有信息。
- **其余设置与 NA2 相同：** 场景、P0 工程 checkpoint、CPU worker、日志组件 v0.4、渲染不计入物理时间，worker 按声明延迟 50 / 150 ms 等待后返回。

## 结果

| 案例 | 计划偏移 L̂（最小 / 中位 / 最大） | 返回时余量（中位 / 最小） | 作废槽位 | 按时生效 | 超限拒绝 | 节奏：延迟 ≤ 1 周期的 tick |
|---|---|---|---|---|---|---|
| 50 ms 朴素 | 0 / 0 / 0 | −5 / −10 | 484 / 800（60.5%） | 110 | 206 | 91.9% |
| 50 ms 补偿 | 0 / 5 / 7 | 0 / −5 | 9 / 800（1.1%） | 178 | 613 | 80.0% |
| 150 ms 朴素 | 0 / 0 / 0 | −11 / −12 | 800 / 800（100%） | 0 | 0 | 98.4% |
| 150 ms 补偿 | 0 / 11 / 11 | 0 / −11 | 8 / 800（1.0%） | 149 | 643 | 92.7% |

- **余量：** 等于计划偏移减去实际经过的 tick。补偿后中位为 0，即动作块正好从返回后的下一个 tick 开始。50 ms 补偿时 L̂ 会随延迟波动变化（最大 7），因此有部分 ticket 多出 1–4 个 tick 的富余。
- **剩余作废：** 150 ms 补偿的 8 个作废全部来自第一个 ticket（L̂=0，经过 11 tick）；50 ms 补偿的 9 个中，5 个来自第一个 ticket，其余来自实际延迟超过了近 8 次最大值的情况。
- **恒等式：** 每个 ticket 的作废数恰好等于 min(8, max(0, 经过 tick − L̂))，reader 逐个核对。
- **视频：** 2×2 原生相机网格，行是延迟，列是调度方式。150 ms 朴素调度下机械臂始终保持初始姿态，补偿调度下能动。
- **节奏代价：** 补偿后可执行的槽位多了，每个 tick 要写的 fsync 事件也多了，50 ms 补偿案例的节奏保真度降到 80%。推理在途期间每个 tick 实际占用的墙钟中位仍为 14.8–15.8 ms。

## 必须同时说明的限制

- **只验证了调度。** 补偿让模型预测更远的未来（最远 L̂+8 个 tick），而输入是更早的观测。动作质量是否因此下降，用 P0 无法判断：P0 已提交目标中约 78–81% 超出关节限位。这项代价要等可用策略出现后才能测。
- **L̂ 取近 8 次最大值是最简单的确定性规则。** 它对延迟突然变长没有保护，第一个动作块也总是作废。这里没有比较更强的预测方法（分位数、方差感知、按动作重要性调整）。
- **仍不是 1:1 实时。** 节奏因子为 4；按真实时间，同样的延迟会吃掉 4 倍的 tick。
- **NA2 记录缺口已修复。** 守卫触发时会写 `GUARD_TRIP.json`（tick、q、qd、越界项、当前目标），CPU 回归测试已覆盖；本轮四个案例都没有触发守卫。
- **不涉及以下内容：** 任务或化学成功、受力资格、S/F/R 准入、M/B3、真机。
